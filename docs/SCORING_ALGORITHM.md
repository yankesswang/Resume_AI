# 履歷評分演算法

本文件說明 Resume AI 的候選人評分流程：每個分數怎麼算出來、每個參數為什麼設成
現在的值，以及哪些設定可以從前端調整。

職缺內容如何透過 LLM 轉換成可編輯的篩選標準，請參考
[JD 篩選標準生成演算法](JOB_PROFILE_GENERATION_ALGORITHM.md)。

所有數值校準都基於實際資料庫中的 **3,179 份履歷**，並在文中標註實測結果。

---

## 1. 總覽

評分分成五個構面，各自產出 0–100 分，再依權重加總為總分：

```
總分 = Σ (構面分數 × 權重)
```

套用職缺專屬 `DomainProfile` 時，若 LLM 已確認候選人在該領域為 Tier 0（工作、研究與
專案皆無相關實作），總分上限為 45。這可避免「溝通、報表、資料分析」等跨產業通用詞
把完全不相關的候選人推入可錄用區間。LLM 無法使用、僅由關鍵字 fallback 判成 Tier 0
時不套用此上限，因為降級結果的證據強度不足以支持硬性壓分。

| 構面 | 預設權重 | 資料來源 | 判斷方式 |
|---|---|---|---|
| AI 經驗深度 | 35% | 履歷全文 + 工作經歷 | LLM 分級 + 關鍵字保底 |
| 工程落地能力 | 20% | 履歷全文 | 關鍵字分級 |
| 語意匹配 | 20% | 履歷 vs 職缺 | Embedding 相似度 |
| 教育背景 | 15% | 學歷欄位 | 學校等級 × 科系相關性 |
| 技能驗證 | 10% | 技能標籤 vs 工作經歷 | 生態分類 + 灌水扣分 |

完整流程：

```
履歷 PDF
   └─> 解析 (Marker / pdfplumber) ──> raw_markdown + 結構化欄位
          │
          ├─ 1. 硬性條件篩選 ──[未通過]──> 總分 10，流程結束
          ├─ 2. 教育背景評分
          ├─ 3. AI 經驗分級   (LLM，結果寫入快取)
          ├─ 4. 工程成熟度
          ├─ 5. 技能驗證
          ├─ 6. 語意相似度   (Embedding)
          └─ 7. 加權總分 + 標籤 + 分析文字
```

程式位置：`app/scoring/pipeline.py`（總流程）、`app/scoring/*.py`（各構面）、
`app/scoring/config.py`（可調參數）。

## 2. AI 經驗深度（35%）

這是權重最高、也最容易出錯的構面。

### 2.1 四個層級

| 層級 | 名稱 | 判斷依據 | 分數帶 |
|---|---|---|---|
| **T0** | Non-AI | 完全沒有 AI/ML 經驗（一般軟體、IT、硬體、QA） | 25–40 |
| **T1** | Wrapper | 只呼叫 API、寫 prompt、做 Streamlit/Gradio demo | 45–62 |
| **T2** | RAG Architect | 設計 RAG/Agent、選型與調校向量資料庫、hybrid search、reranking | 67–84 |
| **T3** | AI Expert | 訓練/微調模型（LoRA、SFT、RLHF）、推論優化（vLLM、CUDA）、或有頂會論文 | 88–100 |

**T0 為什麼必要**：應徵 AI 職缺的人多數並不是 AI 工程師。沒有 T0 時，所有非 AI
背景的人都落在 T1 的 60 分起跳，整個排序被壓平。

### 2.2 分數帶不可重疊

每個層級的分數 = `該層級起始分 + 加分`，加分上限刻意小於層級間距：

```
T0  25 ─────── 40
T1        45 ─────── 62
T2               67 ─────── 84
T3                      88 ─────── 100
```

> **這是曾經發生過的 bug**：舊版加分上限（+20）剛好等於層級間距（20），
> 導致 T2 可拿到 98.3 分、反而贏過 T3 的候選人，層級形同虛設。
> `config.py` 的 `validate()` 現在會擋掉任何重疊設定。

加分來源（三項加總後受該層級上限約束）：

| 加分 | 上限 | 條件 |
|---|---|---|
| 技術棧 | +10 | 命中的技術關鍵字加權總和 × 2 |
| 複雜度 | +5 | 資料規模、系統架構、模型規模三項各 1/3 |
| 量化指標 | +5 | 履歷中出現「降低 30%」「Recall@10」等具體數字 |

### 2.3 LLM 分級 + 關鍵字保底

主要由 LLM 讀履歷判斷層級，關鍵字只做**單向往上修正**：

- LLM 判斷偏低 → 關鍵字保底可往上拉
- LLM 判斷偏高 → **不會**往下修（防吹牛的責任仍在 LLM）

保底門檻為「命中 **2 個以上不同**的高辨識度技術詞」。實測校準：

| 門檻 | 觸發比例 | 判斷 |
|---|---|---|
| 任一 Tier-3 關鍵字 | 71% | 太寬鬆 — PyTorch/Training 多半只是修過課 |
| 1 個高辨識度詞 | 20% | 仍太寬鬆 — CUDA/LoRA 常出現在課程清單 |
| **2 個不同高辨識度詞** | **7.7%** | **採用** — 符合真正模型層級工程師的合理比例 |

高辨識度詞指 vLLM、TensorRT-LLM、QLoRA、RLHF、DPO、DeepSpeed、Flash Attention、
KV Cache、CUDA 等「沒實際做過很難寫出來」的詞；PyTorch、Training、Llama、API
等泛用詞**不列入**。

### 2.4 曾經讓 98% 候選人評分失效的 bug

這是目前分數準確度最關鍵的一課，改動時務必留意。

**現象**：3,179 人中有 3,121 人（**98.2%**）被判為 T1。

**原因**：分級器原本設定 `_INCLUDE_RAW_MARKDOWN = False`，只送結構化欄位給 LLM。
但實際資料中：

- **52%** 的候選人沒有任何 `work_experiences` 資料列
- **42%** 的候選人 `skill_tags` 為空

於是送給 LLM 的內容實際上只有 36 個字元：

```
=== 工作經驗 ===
[]

=== 技能標籤 ===
None
```

LLM 只能回答「查無證據 → Tier 1」。例如候選人 id=2 有 11,918 字的完整履歷，
仍被判 T1。

**修正**：
1. `_INCLUDE_RAW_MARKDOWN = True`，送出履歷全文（預設 12,000 字）
2. 結構化欄位為空時，明確標示為「未擷取到」而非「不存在」，避免 LLM 把
   解析失敗誤讀成候選人能力不足
3. `MODEL_CONTEXT_LENGTH` 預設 4096 → 32768。舊值會把履歷截斷到約 2,000 字，
   等於丟掉大部分證據（實測載入的 qwen3.5-9b 支援 262,144 tokens）
4. 截斷改為「保留頭尾」：工作經歷通常在履歷開頭，而技能、自傳、專案在結尾，
   只留開頭會剛好丟掉 T3 的關鍵證據

## 3. 工程落地能力（20%）

`M_Eng = 後端 + 資料庫 + 前端`，上限 0.7，再正規化為 0–100。

| 構面 | L1 | L2 | L3 |
|---|---|---|---|
| 後端 (0.10/0.20/0.35) | Flask、FastAPI、REST API | Docker、CI/CD、Nginx | K8s、Kafka、gRPC、微服務 |
| 資料庫 (0.05/0.12/0.20) | MySQL、SQL、Pandas | PostgreSQL、MongoDB、ETL | pgvector、Milvus、Neo4j |
| 前端 (0.02/0.05/0.15) | Streamlit、Gradio | HTML/CSS、jQuery | React、Vue、TypeScript |

## 4. 語意匹配（20%）

用 embedding 計算履歷與職缺的 cosine 相似度。

### 4.1 只嵌入職缺的「技能相關欄位」

把整份職缺 JSON 拿去 embedding 會讓薪資、地址、福利、休假制度等樣板文字主導向量。
實測結果：**最強與最弱的候選人只差 0.01**（0.61 vs 0.60），這 20% 權重形同雜訊。

改為只取 `job_summary`、`responsibilities`、`technical_foundation`、
`preferred_qualifications`、`tech_stack_weights` 後（2,506 字 → 837 字）：

| 候選人 | 原始 | 只取技能欄位 | 再拉伸後 |
|---|---|---|---|
| 頂尖 AI (id=57) | 0.6677 | 0.7540 | **0.8686** |
| 一般 (id=33) | 0.5999 | 0.6657 | 0.6161 |
| 不相關 (id=1) | 0.4893 | 0.4955 | **0.1299** |

強弱差距從 0.18 拉開到 0.74。

### 4.2 拉伸（rescale）

Sentence embedding 的 cosine 值天生集中在 0.45–0.80 這個窄帶，直接乘上權重等於
該構面近乎常數。因此線性拉伸到 [0, 1]：

```
rescaled = clamp((sim - 0.45) / (0.80 - 0.45), 0, 1)
```

上下界可在前端調整。

## 5. 教育背景（15%）

```
單一學歷分數 = 學校分數 + 科系分數
綜合分數     = 學士 × 0.7 + 碩士 × 0.3       (有研究所學歷)
             = 學士 × 0.9                    (只有學士)
最終分數     = min(綜合 / 24 × 100, 95) + 論文加分(最多 +5)
```

### 學校等級

| 等級 | 分數 | 範圍 |
|---|---|---|
| S | 15 | 博士學位 |
| A | 10 | 台清交成政台科、QS 頂尖 CS 名校 |
| B | 5 | 中央、中興、中正、中山、北科、師大 |
| C | 2 | 其他國立大學、知名私校、國際知名大學 |
| D | 0 | 其餘 |

> 舊版只有 A/B/C 三級且 C = 0 分，導致 **59.8% 的學歷資料全部是 0 分** —
> 國立雲科大和無名學校同分。新增 C 級後降至 23.7%。

科系相關性：Tier1（資工/電機/資管/AI）10 分、Tier2（統計/數學/物理）3 分、其他 0 分。

論文加分（不受 95 分上限限制）：AI 相關主題 +2.5、頂會/期刊發表 +2.5。

## 6. 技能驗證（10%）

依技術棧生態給基準分，再扣除無佐證的聲稱：

| 生態 | 基準分 |
|---|---|
| LLM Stack | 90 |
| Deep Learning | 70 |
| Traditional ML | 50 |
| General | 30 |

扣分機制（防止技能欄灌水）：

| 情況 | 扣分 |
|---|---|
| 宣稱技能，工作經歷與履歷全文皆無佐證 | −5 |
| 僅出現在作品集/自傳，工作經歷無佐證 | −2 |
| `job_skills` 字數 > `job_description` 兩倍且 > 20 字 | −5 |

下限 10 分。另外，只寫在技能標籤、工作經歷沒提到的關鍵字，在計算技術棧加分時
只以 **0.4 倍**計算。

## 7. 硬性條件篩選

`job_requirement.json` 的 `hard_filters` 若有設定，未通過者直接給 10 分並結束流程，
不再計算其他構面。

---

## 8. 快取機制

LLM 分級結果存在 `candidates.llm_tier`，快取鍵包含：

- `llm_tier_md5` — 履歷內容的 MD5
- `llm_tier_prompt_md5` — prompt 內容的 MD5

因此**修改 prompt 或 `_INCLUDE_RAW_MARKDOWN` 會自動讓舊快取失效**，下次評分自動
重新分級，不會默默沿用舊分數。

> 注意：`llm_tier` 為 0（Non-AI）是合法值。判斷快取是否存在必須用
> `is not None`，用 falsy 判斷會讓 T0 候選人每次都重打 LLM。

## 9. 前端可調參數

導覽列 **評分設定**（`/scoring`）提供以下調整，存檔後寫入 `scoring_config.json`：

| 區塊 | 可調內容 |
|---|---|
| 評分權重 | 五個構面的權重（自動驗證總和 = 100%，並提供一鍵正規化） |
| AI 層級分數帶 | 每層級的起始分與加分上限，即時顯示區間是否重疊 |
| 關鍵字保底 | 開關、最少命中訊號數 |
| 語意相似度 | 拉伸上下界、技能標籤權重係數 |
| 學歷分數 | 五個學校等級、三個科系等級的配分 |
| 技能生態 | 四種生態基準分、三種扣分幅度 |

### 試算功能

按「試算影響」會取分數最高的 40 位候選人，**同時**用目前設定與新設定重新計算，
顯示每個人的分數變化與平均變動。此操作：

- 使用既有 LLM 快取，**不會**重新呼叫模型（快速、零 LLM 成本）
- **不會**寫入任何檔案，純預覽

### API

```
GET    /api/scoring-config            # 目前設定 + 預設值
PUT    /api/scoring-config            # 驗證並儲存（失敗回 400 與錯誤訊息）
POST   /api/scoring-config/validate   # 只驗證不儲存（前端即時檢查）
POST   /api/scoring-config/reset      # 還原預設，刪除覆寫檔
POST   /api/scoring-config/preview    # 前後對照試算
```

設定檔路徑可用 `SCORING_CONFIG_PATH` 環境變數指定，預設為專案根目錄的
`scoring_config.json`。該檔不存在時即使用內建預設值。

**儲存後需重新執行評分**（批次比對）才會套用到既有候選人。

## 10. 修改前必讀

以下每一條都對應一個已經發生過、且有實測數據佐證的問題：

1. **分級器必須讀得到履歷全文** — 關閉後 98% 候選人會塌縮成同一級
2. **`MODEL_CONTEXT_LENGTH` 必須與 LM Studio 實際設定相符** — 太低會靜默截斷履歷
3. **層級分數帶不可重疊** — 否則高分低層級會贏過低分高層級
4. **關鍵字保底需要 2 個以上不同訊號** — 1 個會讓 20% 履歷誤判為 T3
5. **只嵌入職缺的技能欄位** — 否則樣板文字會主導向量，鑑別度歸零
6. **Tier 0 是合法值** — 後端快取與前端顯示都不可用 falsy 判斷（`0` 會被當成「沒有」）

### 目前實測分布（80 人隨機樣本）

| | 修正前 | 修正後 |
|---|---|---|
| 層級分布 | 98.2% 集中在 T1 | T0:4 / T1:32 / T2:32 / T3:12 |
| 標準差 | 8.6 | **11.48** |
| 分數範圍 | 33.8–83.7 | 40.1–95.9 |
